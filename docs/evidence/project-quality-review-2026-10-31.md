# 项目质量与重构评估

日期：2026-10-31  
版本：2.0.0-beta.14  
性质：源码核查、本机运行与实际 CI 结果的评估记录；不是已执行的重构方案。

## 结论

**项目基础设计是好的，但距离“优秀作品”仍有明确差距。值得做结构性重构，不值得推倒重写。**

当前评价：有良好架构基础和较扎实核心验证的 Beta 产品；还不能称为验证闭环完整、生命周期边界清晰的成熟作品。

即使完全不考虑工作量，也不建议重写。重写不会自动解决权限、时序和跨应用协议问题，反而会重新暴露已经处理过的边界。应保留可靠部分，重构那些让正确性难以验证的边界。

## 评估范围与证据口径

- 核查偏好传递、命令协议、请求关联、UI 粘贴编排、文件拆分、跨平台实现、测试配置及发布流程。
- 评估开始时查看的提交为 `90a0fd9e5826a420e7ecec44d834d75ad931e109`；结束前读取的 HEAD 为 `ed98d0e60fbad90b7309d50c71bce31f379c0c9b`。期间仓库发生了非本次评估产生的更新，因此本机检查是本轮各执行时点的结果，不宣称所有检查都针对一个冻结提交。
- 下文 CI 结果固定到明确的运行编号及提交，不代表后续分支状态。
- 源码链接的行号按评估时点记录，后续修改可能移动。
- 区分已确认事实、维护风险与尚未复现的故障；没有把测试通过等同于完整产品验收。
- 本轮未修改生产代码；临时统计脚本已删除。

## 一、对初步判断的修正

| 初步判断 | 核查结果 |
|---|---|
| 格式保真仅 Windows 实现 | **错误。** Unix 也枚举原生格式、读取额外载荷，并在 Original 复制时写回；核心存储没有绑定 Windows 格式。 |
| macOS/Linux 只有编译验证 | **错误。** 下述固定提交的两个平台均已通过原生 CI 测试、打包和窗口冒烟。 |
| 粘贴请求全靠散落字段，没有类型保护 | **夸大。** 已有 `PendingRequest<T>`、请求代次校验、集中取消入口及相关回归测试。 |

## 二、真正影响质量的问题

### 1. 发布验证尚未形成可靠闭环

优先级最高。检查了实际 GitHub Actions 结果，不只是 workflow 配置。

提交 `ed98d0e60fbad90b7309d50c71bce31f379c0c9b`，GPUI CI 第 77 次运行：

| 平台 | CI 结果 |
|---|---|
| Windows | **Tests 失败**；剪贴板往返和 Release 构建被跳过。 |
| macOS 15 | 检查、测试、原生打包、DMG 启动冒烟全部通过。 |
| Ubuntu 24.04 | 检查、测试、X11 专项回归、原生打包、窗口冒烟全部通过。 |

证据：

- [运行 #77](https://github.com/Y-ASLant/ElegantClipboard/actions/runs/41166737177)
- [Windows job](https://github.com/Y-ASLant/ElegantClipboard/actions/runs/41166737177/job/124435819565)
- [Ubuntu job](https://github.com/Y-ASLant/ElegantClipboard/actions/runs/41166737177/job/124435819584)
- [macOS job](https://github.com/Y-ASLant/ElegantClipboard/actions/runs/41166737177/job/124435819655)
- [前一提交的运行 #76](https://github.com/Y-ASLant/ElegantClipboard/actions/runs/41163949454)：同样在 Windows Tests 阶段失败。

**本机测试通过，不能抵消 CI 失败。** 详细日志请求返回 HTTP 403；公开 job 页面也提示日志不可用。目前只能确定失败阶段，不能断言是产品缺陷、测试不稳定还是 runner 环境问题。

另外，[Release workflow](../../.github/workflows/release.yml#L73) 只依赖各平台打包任务，没有测试通过的依赖条件；[Windows 打包脚本](../../scripts/package-gpui-windows.ps1#L16)和 [Unix 打包脚本](../../scripts/package-gpui-unix.ps1#L19)主要执行 Release 构建。最终生成的是发布草稿，不是自动正式发布，但仍缺少明确的自动质量门槛。

建议：

- 查清 Windows CI 的具体失败原因，不能用忽略测试或反复重跑掩盖。
- 发布验证绑定同一个提交：测试、必要的原生往返和包内启动通过后，才允许进入发布流程。

这比调整文件大小、引入更多抽象更直接地影响作品质量。

### 2. UI 文件拆开了，但状态仍过度集中

这是最值得重构的部分。实测：

- `ClipboardView` 有 **165 个字段**。
- `ui/` 下 **38 个文件**实现 `ClipboardView` 方法。
- **64 个文件**使用 `use super::*`。

见 [ClipboardView](../../crates/clipboard-gpui/src/ui.rs#L237)。

字段覆盖历史、选择、粘贴、引导、偏好、拖拽、预览和窗口生命周期等多个领域。单一 GPUI 视图负责协调这些领域很正常，但它还持有大量领域内部状态，兄弟模块可以直接操作这些状态。

实际影响：

- 修改隐藏窗口、失焦、重新唤出等行为，需要同时理解粘贴、序列、选择和预览的规则。
- 测试容易停留在小原语层，难以验证完整交互转换。
- 按钮禁用、取消和错误恢复条件可能在不同入口产生差异。

历史上确实修复过“首条序列请求误清队列”“正常回贴误取消”等问题，见[变更记录](../CHANGELOG.md#L78)。这证明生命周期协调是实际风险点，但不意味着这些故障现在仍存在，也不能仅凭历史故障证明字段数量是唯一根因。

**建议重构方向：按状态所有权拆分，而不是继续拆文件。**

优先收敛粘贴协调状态及其转换接口，其次才是选择、预览和偏好保存状态。外层视图负责调用和渲染，不直接修改各领域内部字段。

不应简单塞进一个巨大的 `Idle/Single/Batch/Sequence` 枚举：**序列队列与当前单条投递本来就可以同时存在。** 应分别建模队列和投递阶段，再由一个协调入口维护关系。

### 3. 命令协议的问题不在“大”，而在重复维护行为分类

当前有 **80 个 Command、62 个 Event**。对现有功能量而言，这本身不是缺陷。

真正的风险是新增复制变体时，需要同步维护：

- worker 执行分支；
- 是否取消旧粘贴的分类；
- 失败回执归属；
- UI 发起与消费逻辑。

例如：

- [replacement_request](../../crates/clipboard-gpui/src/ui/paste_delivery.rs#L4) 枚举哪些命令替换剪贴板。
- [failure_kind](../../crates/clipboard-platform/src/service/protocol.rs#L262) 枚举哪些失败属于粘贴请求。

两处都有兜底分支，**漏掉一种新操作不一定导致编译错误**。这是维护风险，不是本轮发现某个现有变体漏接。

建议收敛复制模式、操作目的和请求身份的表达，让这些策略从同一份类型信息推导；保留显式、可读的命令分发，不引入通用消息框架或宏注册系统。

这属于有明确收益的内部协议重构，不需要改数据库或备份格式。

### 4. 偏好持久化存在维护风险，但没有发现当前丢数据

备份过滤使用一条[手写白名单 SQL](../../crates/clipboard-core/src/preferences.rs#L39)。

核查结果：

- 当前 29 个偏好键都在白名单里，**没有发现遗漏**。
- 新增偏好必须另外修改这个列表。
- 现有[备份往返用例](../../crates/clipboard-core/src/backup/tests.rs#L50)没有完整覆盖最近新增的去重策略、恢复剪贴板、序列热键等偏好。

**影响是未来的静默回退风险，不是已证实的数据丢失。**

应收敛键名与备份规则的维护来源，并补充真实的“设置非默认值 → 导出 → 恢复 → 验证仍然生效”覆盖，而不是测试源码字符串是否相等。

`Service.initial_*` 可以聚合成启动偏好快照；UI 普通保存状态也可以继续复用现有 `PendingPref<T>`。但主题、语言、热键注册的副作用不同，不能为了统一而强行套同一个处理器。

### 5. 自动恢复剪贴板有无法忽视的保证边界

当前代码在成功注入粘贴按键后发送恢复命令，见 [paste_delivery.rs](../../crates/clipboard-gpui/src/ui/paste_delivery.rs#L95)。

**按键注入成功不代表目标应用已经读取剪贴板。** 请求编号和序列校验能防止恢复错请求、覆盖外部新复制，却不能证明目标已消费内容。

这是已确认的设计限制，**不是本轮复现的故障**；功能默认关闭是合理的。[跨平台正确性验证记录](cross-platform-correctness-2026-10-27.md#L45)也明确说明了这一限制，以及 Unix 缺少原子比较写入接口的差异。

优秀作品需要对这条路径做慢响应目标、跨进程、权限不同和连续粘贴验证。不能用一个固定延迟就宣称解决了时序问题。

## 三、跨平台适配的真实水平

**不是两个空壳移植层，而是有真实原生实现、也有原生 CI 通过证据的跨平台应用。**

但距离各平台体验成熟还有差距：

- **macOS：**辅助功能权限授予/撤销、同应用多窗口目标识别仍需真实交互验收；目前只有 ad-hoc 签名，没有 Developer ID 签名和公证，分发体验有明显门槛。
- **Linux X11：**热键、XTEST、XDND 等有真实实现及专项验证；仍需覆盖不同桌面、托盘宿主和真实目标应用。
- **Wayland：**当前明确缺少全局热键、自动粘贴、来源识别和精确定位，且依赖 data-control。不能把 Xvfb 下的 X11 成功外推为 Wayland 成熟，也不能把当前限制一概认定为永久无法实现。
- **共享服务测试：**有 **66 项服务测试被整个 `windows` 条件挡住**，其中大量是历史、偏好、分组和事件行为，而不是 Windows 专属操作。见[测试入口](../../crates/clipboard-platform/src/service/mod.rs#L32)。

应把真正共享的服务测试迁到共享测试模块，保留系统专属夹具；不是直接删掉 `cfg` 就算完成，也不能让测试操作用户日常桌面的剪贴板或全局热键。

平台能力及分发限制见[根 README](../../README.md#平台差异)；尚待真实目标应用验证的项目见[跨平台验证记录](cross-platform-correctness-2026-10-27.md#L46)。

**跨平台方向值得保留，当前缺口主要是行为验证和分发体验，不是架构选错。**

## 四、重构边界与投入顺序

### 应保留

- 三层依赖方向：`clipboard-gpui → clipboard-platform → clipboard-core`。
- 共享业务与平台实现分离。
- 串行 worker、有界队列、请求代次。
- 已有迁移、备份、隐私和格式保真处理。
- GPUI Kit 与现有原生界面路线。

### 建议顺序

1. **闭合 Windows CI 与发布门槛。** 明确失败根因，建立同一提交的验证链路。
2. **重构 UI 状态所有权，优先粘贴生命周期。** 目标是取消、失败、重入、正常回贴与用户打断有可独立验证的转换规则，而不是仅减少字段或文件行数。
3. **收敛复制协议的重复分类和偏好持久化维护点。** 避免新功能需要同步多份隐含策略清单。
4. **补齐共享服务的跨平台测试与真实目标应用验收。** CI 窗口启动不能替代权限切换、跨应用回贴和格式优先级验证。
5. **建立性能和体验的量化验收基线。** 包括大历史搜索、图片滚动、后台资源占用、持续运行、多显示器和不同 DPI。本轮未测这些，不能仅凭 Rust、虚拟列表和小体积就判定性能优秀。

不建议为减少显式代码而增加无当前消费者的框架、注册表或动态分发层，也不建议单纯放宽行数限制来回避职责问题。

未完成的验证：

- 全面视觉审查与完整原生交互矩阵。
- macOS/Linux 人工桌面交互与权限验收。
- 慢响应目标和跨应用的自动恢复剪贴板时序验证。

**优秀作品的下一步不是“让代码看起来更高级”，而是让状态转换更容易证明正确，让每次发布都有可信的行为证据。**
